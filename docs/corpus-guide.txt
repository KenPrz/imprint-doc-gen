IMPRINT-DOC-GEN DOCUMENT CORPUS V1

Purpose
  100 DOCX levels and 100 XLSX levels, each with a template, JSON input,
  attachment mapping, expected document, hashes and a machine-readable recipe.
  The 100 levels are ten cumulative feature bands with ten parameter steps each.
  They are not 100 separate implemented engine features or a proof of full Office
  compatibility. A new band retains earlier bands at their maximum severity.

What obfuscation means here
  Valid packaging and document complexity: fragmented placeholders, shared rich
  strings, namespace aliases, nonsequential relationship IDs, XML comments,
  shuffled ZIP entries and stored versus compressed members. Files are neither
  encrypted nor deliberately malformed. Rejection tests belong in another suite.
  Revision 2 writes ZIP local sizes explicitly (no streaming data descriptors)
  and keeps default namespaces in package content-types and relationship files.
  LibreOffice rejected certain DOCX variants of those packaging representations;
  namespace alias challenges remain in document and worksheet XML content.

Commands (Node.js 24; application and fixture code are TypeScript)
  npm ci --ignore-scripts
  npm run typecheck
  npm test
  npm run corpus:generate
  npm run corpus:validate
  npm run corpus:score -- /absolute/path/to/engine-output

Dependencies have exact versions recorded in package.json and package-lock.json.
ZIP/XML libraries are shared by the fixture tools and production engine.
Generation can also write elsewhere: node scripts/corpus/generate.ts /tmp/corpus-copy
Generation replaces the four generated files within each known case directory;
it does not delete other files. Do not hand-edit generated files; edit the builders.

Template dialect: carbone-style-v1
  All 100 DOCX and 100 XLSX template files use {d.path} bindings. The expected
  output documents are unchanged from the earlier corpus; this migration must
  preserve values, styles, layout, pictures and formulas.
  {d.title} reads root data, including inside repetition. {d.items[i].name}
  selects the current array item. A matching {d.items[i+1].name} row or paragraph
  terminates the pattern and is discarded. Empty/missing/null arrays remove it.
  DOCX supports nested full paths such as {d.groups[i].items[i].name}; XLSX
  currently supports one-row object-array patterns with adjacent marker rows.
  Missing/null scalars become blank; false/zero retain their values. Inserted
  data is escaped and never reinterpreted as template syntax. Use the first
  placeholder character's run formatting for replacement text.
  Picture alternative text {d.red} selects attachment "red". DOCX item pictures
  use {d.items[i].image}; root fields can also contain attachment keys or PNG/JPEG
  data URLs. Geometry and independent placements are preserved. Remote image
  URLs and SVG are unsupported. Missing optional images retain their placeholder.
  Full syntax, scope and limits: docs/template-syntax.txt. Legacy double-brace
  syntax remains regression-tested but is not generated by this corpus.

XLSX rules
  Implemented: root scalar bindings in inline/shared strings, rich text,
  typed numbers/booleans, null -> blank whole cell, and PNG/JPEG picture replacement.
  Literal attachment keys and root data paths are supported on picture metadata.
  Existing one-cell/two-cell/absolute anchor geometry is retained.
  Cells preserve style indices. Line breaks/tabs and Excel escape sequences are
  supported in strings; the cell limit is 32,767 UTF-16 code units.
  Without loops, existing formulas/caches are preserved and recalculation is
  requested. With loops, the bounded calculator refreshes all supported formulas.
  Formula placeholders, date conversion and bound phonetic strings are unsupported.
  Implemented loops select exactly one row, accept arrays of objects and remove
  the [i+1] marker row. Empty arrays remove both exemplars. Multiple independent
  loops and explicit root {d.path} bindings are supported; nested/multi-row XLSX loops are not implemented.
  Row/range rewrites distinguish structural movement from relative formula copies.
  Existing pictures below a loop move; overlapping pictures and merges are rejected.
  The calculator supports arithmetic/comparison/text expressions, A1 ranges and
  SUM/MIN/MAX/AVERAGE/COUNT/IF, with cross-sheet dependencies and typed errors.
  It rejects advanced functions, named operands, whole-row/column references,
  shared/array/data-table formulas, boolean concatenation and ambiguous zero powers.
  Loop workbooks with charts, pivots, comments or unsupported extensions require
  later adapters. Explicit coordinates, iteration/byte/formula budgets are enforced.
  A full-cell scalar keeps its JSON type: number -> numeric cell, boolean -> b.
  Strings beginning with '=' remain literal strings, never executable formulas.
  Shared-string and inline-string representations are semantically interchangeable
  when text and rich formatting are preserved. Shared-string table order is not
  compared. Existing formula references and cached values are checked.
  Repeated rows rebase relative formula references; absolute and mixed references
  remain meaningful. Cells below the insertion move by the inserted row count.
  Dependent table/filter/name/validation/conditional-formatting ranges expand.
  Marker-row removal participates in formula/range/anchor coordinate updates.
  The renderer and corpus do not implement a general Excel calculation engine.

Engine integration
  Render each case using its template, input.json and resolved attachment mapping.
  Write outputs to <output>/docx/level-001.docx and
  <output>/xlsx/level-001.xlsx, through level-100 for both formats.
  Run corpus:score against that output directory. Missing outputs are NOT RUN,
  not passes. Exit code 0 means every semantic check passed, 1 means failures,
  and 2 means incomplete coverage without failures. The report gives passed/failed/
  unsupported/not-run and highest contiguous passing level separately for each format.
  The scorer compares supplied files; it does not prove which engine generated
  them. Never copy expected files into the output folder and report engine success.

What validation establishes
  ZIP CRCs, XML parsing, content-type coverage, relationship integrity, scalar
  values, typed cells, formulas, structural snapshots, picture bytes/geometry,
  selected style and layout preservation, and untouched preservation parts.
  Mutation tests prove wrong text/images/formulas/styles/ranges are detected.
  Namespace aliases, relationship IDs and ZIP ordering are not correctness tests.
  The snapshot currently expects generated part paths and selected style indices;
  engines that legitimately rename parts or rewrite equivalent style tables will
  need an expanded semantic normalizer before cross-engine scoring is fair.
  Formula cached values are required by this baseline. An engine relying solely
  on Excel recalculation needs a separate recalculation adapter before comparison.
  Templates and reference outputs share low-level builders. Independent assertions
  from input data and mutation tests reduce correlated mistakes, not eliminate them.

What has NOT been established
  Full OOXML schema conformance, Word/Excel repair-free opening, layout/pagination
  fidelity, PDF visual equivalence, production performance, or engine compatibility.
  Docker supplies LibreOffice independently of the host installation. See
  docs/milestone-1-validation.json for measured conversion and visual checks.
  Do not mark visual validation passed on the basis of XML/package tests.
  Generated fixtures require an independent Office application review before being
  accepted as visual goldens. Synthetic cases should later be joined by consented,
  anonymized real-world templates and minimized reproductions of production bugs.
