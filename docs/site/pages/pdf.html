PDF operations

Merge PDFs, select pages, apply text watermarks and numbering, and attach supporting files.

Merge and select pages

POST /v1/pdf
{
  "inputs":[
    {"bytes":"BASE64_FIRST_PDF", "pages":[1,3]},
    {"bytes":"BASE64_SECOND_PDF"}
  ],
  "watermark":{"text":"DRAFT", "opacity":0.2, "rotation":30},
  "pageNumbers":true,
  "attachments":[{"name":"details.csv", "bytes":"BASE64_CSV", "mimeType":"text/csv"}]
}

Page indexes are one-based. Omitting pages selects all pages in that input. Inputs and selected indexes define output order; duplicates are allowed. The response is binary PDF. Page numbers appear at the bottom center.

Split into groups

POST /v1/pdf/split
{"bytes":"BASE64_PDF", "ranges":[[1,2],[3],[4,5]]}

The response is {"documents":["BASE64_PDF",...]}. SDK exports processPdf({inputs,...options}) and splitPdf(bytes, ranges) accept byte arrays and return buffers.

Assemble a bundle from uploads

POST /v1/pdf/bundle assembles real-world uploads (a rendered document followed by quotes, invoices and photos of receipts) into one PDF. It takes multipart/form-data, so large files avoid base64 and the 16 MiB JSON limit. POST /v1/pdf is unchanged. 

curl -X POST https://imprint.example/v1/pdf/bundle \
  -H "Authorization: Bearer $IMPRINT_API_KEY" \
  -F decrypt=true -F flatten=true -F stripActiveContent=true \
  -F files=@rendered.pdf -F files=@quote.pdf -F files=@receipt.jpg \
  -o bundle.pdf
Part Meaning
files File parts in output order (by default 1–50, each at most 10 MiB and 200 MiB in total; see the limits below). PDF, JPEG, PNG, WebP or GIF (first frame), detected from the bytes. BMP and HEIC are unsupported.
decrypt true removes an owner password (one that only restricts editing or printing). A PDF that needs a password to open still fails with PDF_PASSWORD_REQUIRED.
flatten true draws form fields and signature appearances into the page as static content. Cryptographic signature validity is not preserved, only the visible appearance. A visible widget without an appearance fails with FORM_APPEARANCE_MISSING; dynamic XFA forms fail with XFA_UNSUPPORTED.
stripActiveContent true removes JavaScript, Launch, SubmitForm, ImportData, GoToR and Rendition actions, additional actions (AA), XFA and any OpenAction, including actions nested inside annotations. The Imprint-Stripped-Active-Content response header lists what was removed per one-based input, for example 2:A+OpenAction, 5:AA. Stripping is not sanitization or malware scanning.
pageSize A4 (default) or Letter for image pages. Each image gets its own portrait page, is turned upright from its EXIF orientation, and is scaled to fit inside 0.5 in margins with its aspect ratio kept. Images are never enlarged and are stored at no more than 300 dpi.

Every flag defaults to false. With no flags, the bundle rejects every input that /v1/pdf rejects. Each input runs through decryption, then its own 256 MiB worker for flattening, stripping and the security scan, one input at a time, before pdfcpu merges the checked files from disk. The response is the binary PDF.

Limits are settings, not fixed values. The defaults are the measured bounds below. Any positive integer is accepted. A value past the measured bounds, or a staging directory that is RAM-backed or too small for a full bundle, logs a warning at startup instead of refusing to start. Re-run npm run bench:pdf-bundle on the target host after raising them.

IMPRINT_REQUEST_TIMEOUT_MS 100000 Time to receive any request, including the bundle upload. 200 MB in 100 s is about 16 Mbit/s.
IMPRINT_PDF_BUNDLE_DIR OS temp directory Staging directory. Use a disk volume; the shipped compose files set /data/bundles.
  • 1,000 output pages at most. Over-limit uploads return 413 (LIMIT_EXCEEDED for the total). Errors name the failing input, for example Input 3: Cannot read PDF….
  • One bundle runs at a time per process and also uses one render admission slot. A busy server answers 503 with Retry-After.
  • Uploads are staged in a private per-request directory and removed when the request ends. The compose files avoid /tmp because it is a RAM-backed tmpfs counted against the container memory limit (128 MB in split mode).
  • Measured bounds (2 cores, staging on disk). 20 × 10 MB of photos and PDFs: about 10 seconds, API peak about 470 MiB, pdfcpu merge about 155 MiB. Worst case, 50 × 12-megapixel photos (about 180 MiB): about 25 seconds, API peak about 560 MiB, merge about 220 MiB. Both fit the 2 GB standalone container. In split mode the worst case is close to the 768 MB API limit; raise mem_limit to 1 GB if bundles are photo-heavy.
  • The plugin dependency is @fastify/multipart; pdfcpu 0.16.1 ships in the API, standalone and converter images.

Limits and document behavior

  • At most 20 inputs, 1,000 source/output pages and 32 MiB combined input/attachment bytes. Output is also bounded at 32 MiB.
  • At most 20 attachments with unique simple filenames. At most 20 split groups and 1,000 selected pages across groups.
  • HTTP operations run in a 256 MiB worker with a 30-second deadline and shared admission capacity.
  • Watermarks use built-in Helvetica and its supported Latin character set. Unsupported characters fail explicitly.
  • Encrypted, signed, interactive-form and detected active-content PDFs are rejected, including actions nested directly inside annotations (checked since 1.1.1). This is document assembly, not a PDF sanitization or malware-scanning service.
  • Assembly copies pages into a new document. Document-level bookmarks, original attachments, metadata and cross-document navigation are not guaranteed to survive. Supply attachments explicitly.
  • No PDF/A, PDF/UA, digital signature or redaction conformance is claimed.

Low-level PDF manipulation uses pdf-lib behind Imprint's validation and execution limits.
