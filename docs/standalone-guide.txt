Imprint Doc Gen: standalone deployment and PMS integration
=========================================================

Deployment contract
-------------------
One linux/amd64 image contains Node.js, the compiled TypeScript API/renderer,
SQLite, Gotenberg and LibreOffice. Only port 3000 serves clients. The converter
listens on loopback port 3001, rejects outbound content fetches, and recycles
LibreOffice after every attempt. tini reaps processes; the supervisor exits
nonzero if the API or converter dies. Docker's restart policy restarts the unit.
GET /health is liveness; GET /ready checks SQLite and the converter.

Use one container per local data volume. This release does not provide shared
network-filesystem storage, horizontal replicas, PostgreSQL or S3 adapters.
PDF processes and API share container resources. Start with 2 CPUs, 2 GiB RAM,
and sufficient disk for the image, SQLite database/WAL and backups.

Pulling a published image
------------------------
GitHub Actions publishes only after the fixture, conversion and standalone
integration jobs pass. The development branch publishes standalone-preview;
main publishes standalone. Every publication also has an immutable sha-<commit>
tag. Prefer the printed registry digest for deployment pinning and rollback.
A tag is not available until its publish job succeeds. The package remains
private; authenticate Docker with a GitHub token that has read:packages access
to KenPrz/imprint-doc-gen. Do not put tokens in source control or command args.

  docker login ghcr.io -u YOUR_GITHUB_USERNAME
  docker pull ghcr.io/kenprz/imprint-doc-gen:standalone-preview

Set IMPRINT_API_KEY to a randomly generated secret of at least 24 characters
in your shell or secret manager. It is the installation administrator key and
also authenticates the default tenant. Use a dedicated tenant key for your PMS.

  docker run -d --name imprint-doc-gen --restart unless-stopped \
    --stop-timeout 120 --memory 2g --cpus 2 --pids-limit 384 \
    --read-only --tmpfs /tmp:rw,size=768m,mode=1777 \
    --cap-drop ALL --security-opt no-new-privileges:true \
    -p 127.0.0.1:8088:3000 -e IMPRINT_API_KEY \
    -v imprint-data:/data \
    ghcr.io/kenprz/imprint-doc-gen:standalone-preview

The named volume is initialized for UID/GID 1001. A host bind mount must be
writable by that UID/GID. The API is loopback-bound on the host; attach it to
your PMS Docker network and use http://imprint-doc-gen:3000 from another
container, or put an authenticated TLS reverse proxy in front of host access.
The existing compose.yml/compose.override.yml retain the two-container dev
workflow. Both now persist service data in an app-data volume (UID 1000).
Do not exchange these volumes without explicitly adjusting ownership.

Building locally, before or instead of registry publication:

  docker build -f Dockerfile.standalone -t imprint-doc-gen:standalone .
  IMPRINT_IMAGE=imprint-doc-gen:standalone docker compose -f compose.standalone.yml up --no-build -d

Using the published image with Compose:

  docker compose -f compose.standalone.yml pull
  docker compose -f compose.standalone.yml up --no-build -d

Authentication and ownership
----------------------------
Every /v1 endpoint requires Authorization: Bearer <key>. Keys stay in the PMS
backend, never in a browser bundle. No client-supplied tenant ID selects the
owner: identity comes from the key. Cross-tenant resource IDs return 404.
The administrator's data requests operate on the default tenant, not on every
tenant. The administrator can provision/rotate/revoke tenant keys:

  POST   /v1/tenants             {"name":"My PMS"} -> {id,name,apiKey}
  GET    /v1/tenants             -> {tenants:[{id,name,keyActive}]}
  POST   /v1/tenants/:id/key     -> {id,apiKey} (invalidates the previous key)
  DELETE /v1/tenants/:id/key     -> {id} (revokes access immediately)

Store returned tenant keys securely; the database stores only their SHA-256
hash. To rotate the default/administrator key, change IMPRINT_API_KEY and
restart. Existing tenant keys and data remain valid. Revocation prevents new
requests; it does not cancel work already accepted.

Template lifecycle
------------------
  POST /v1/templates
    {"name":"Guest invoice","template":"<base64 DOCX or XLSX>"}
    -> 201 {templateId,versionId,format,createdAt}

  POST /v1/templates/:id/versions
    {"template":"<base64 DOCX or XLSX>"}
    -> 201 {templateId,versionId,format,createdAt}

Uploads compile in a worker with the same memory/time limits as rendering.
They validate template structure; missing job data or attachments are checked
when rendering. Every upload is an immutable version; uploads do not publish.

  POST /v1/templates/:id/publish {"versionId":"..."}
    -> {templateId,versionId}

Publishing sets the default version for subsequent jobs. Publishing an older
version rolls back that default. Each submitted job records its resolved
version immediately, so changing the default cannot change an accepted job.
An explicit versionId allows rendering a draft without publishing it.

  GET /v1/templates      -> latest 100 template metadata records
  GET /v1/templates/:id  -> metadata plus all its versions
  DELETE /v1/templates/:id -> 204 (only after all its jobs have been deleted)

Template metadata uses id, name, publishedVersion and createdAt. Version
metadata uses id, templateId, format and createdAt. Timestamps are Unix epoch
milliseconds. There is no individual version mutation/deletion endpoint.

Durable generation
------------------
  POST /v1/jobs
  Idempotency-Key: booking-42-invoice-revision-3
  {
    "templateId":"...",
    "versionId":"optional-explicit-version",
    "data":{"guest":"Alex Rivera"},
    "attachments":{"logo":"<base64 PNG/JPEG>"},
    "output":"pdf"
  }

Returns 202 with {id,templateId,versionId,status,attempts,createdAt,updatedAt,
deadline,error,format,downloadUrl} and Location: /v1/jobs/:id. Omit output to
keep the template format. DOCX-to-XLSX conversion is not supported.

  GET /v1/jobs/:id        -> same status structure
  GET /v1/jobs/:id/result -> binary output (409 until succeeded)
  DELETE /v1/jobs/:id     -> 204 for terminal jobs; 409 while queued/running

Statuses are queued, running, succeeded, failed. Save the job ID on your PMS
booking record and poll from background work. A polling timeout is not proof
that generation failed; continue polling the saved ID. No webhook is sent.

A repeated Idempotency-Key with the same JSON body returns the same job (200),
including after a publish change or service restart. Different body/property
ordering with that key returns 409 IDEMPOTENCY_CONFLICT. Keys are tenant-scoped
and valid while the job is retained. Deleting/expiring a job releases the key.
Use a new key for a new business revision. There is no automatic HTTP submission
retry in the example client; retries should reuse the exact body and key.

Queue and persistence guarantees
-------------------------------
SQLite WAL with synchronous=FULL commits accepted jobs before acknowledging.
Template bytes, attachment/data payloads, output bytes and state live in the
same database so status and bytes commit atomically. This deliberately keeps
the first standalone storage adapter small; PostgreSQL/S3 are future adapters.

At most two uploads/renders execute concurrently, shared with POST /v1/render.
Jobs wait in the queue; synchronous requests return 503 BUSY when capacity is
full. Rendering has a 30-second deadline; complete PDF transfer has 65 seconds.
Transient CONVERSION_FAILED and RENDER_FAILED errors retry once after 2 seconds.
Invalid input, unsupported templates and timed-out conversions do not retry.

A running job has a 150-second lease. After a forced kill, queued work resumes
and interrupted work becomes eligible when that lease expires, up to two total
attempts. A stale attempt cannot overwrite the result of a new lease. This is
at-least-once execution, not exactly-once execution. There are no external job
side effects such as email delivery. A job not started within 24 hours fails
with JOB_EXPIRED; a job already running may finish after that deadline.
Graceful shutdown stops claims and drains active work; allow 120 seconds before
Docker force-kills the container. A crash during response delivery can leave a
committed job, which is why clients should supply an idempotency key.

Terminal inputs/attachments are cleared logically when processing finishes.
Results and error records expire seven days after completion; cleanup runs
roughly once per minute. Templates persist until explicitly deleted. Deleted
SQLite pages may remain in the database/WAL until reused/checkpointed; logical
deletion is not a secure erase. Set backup retention to suit your PMS data.

Budgets: 16 MiB HTTP body; existing 8 MiB archive/image/part and 32 MiB expanded
package bounds; 32 MiB maximum result. Submission reserves result capacity.
Logical storage is capped at 1 GiB per tenant and 4 GiB overall. There are at
most 100 active jobs per tenant/1000 overall, 2000 retained jobs per tenant/
10000 overall, 1000 template versions per tenant, and 1000 tenant records.
Metadata and WAL overhead are outside logical byte quotas: monitor disk space.
Deleting results permits reuse of database pages; it need not shrink the file.

Error additions: 403 forbidden administrator action; 404 missing/not-owned;
409 unpublished template, idempotency conflict, active/in-use resource or
result not ready; 413 storage/version/history limit; 503 queue/capacity limit.
Existing /v1/render statuses and binary response contract remain supported.

PMS example
-----------
examples/pms/client.ts is a dependency-free server-side TypeScript HTTP client.
examples/pms/generate.ts uploads/publishes a sample guest-invoice template,
submits booking.json plus logo.png, polls, and downloads the result.
The checked-in DOCX and XLSX examples include repeated line items; XLSX uses
native number cells and calculated line/subtotal formulas. Replace logo.png
and edit the templates in Office for your property. DOCX displays amounts
formatted by the PMS; this service does not perform currency rounding for it.

With Node.js 24 on your PMS/development machine:

  IMPRINT_URL=http://127.0.0.1:8088 node examples/pms/generate.ts pdf
  IMPRINT_URL=http://127.0.0.1:8088 node examples/pms/generate.ts docx
  IMPRINT_URL=http://127.0.0.1:8088 node examples/pms/generate.ts xlsx

Set IMPRINT_API_KEY to the provisioned PMS tenant key before running. Outputs
are artifacts/booking-invoice.<format>. The demo creates a new template each
run; your PMS should upload only when editing a template and keep its IDs.

Backup and updates
------------------
Stop the container before copying the complete data volume (including any
SQLite WAL files); restart after the snapshot/copy completes. Do not copy just
a live imprint.sqlite file. Keep the snapshot and image digest together.
Restore into an empty volume with UID/GID 1001 ownership for standalone.
Never use docker compose down --volumes when you want to keep production data.

For upgrades, back up first, pull the reviewed digest and recreate the container
with the same volume. The app rejects a newer schema version than it supports;
rolling back across a future schema migration may also require the matching
backup. This release introduces schema version 1 and no destructive migration.

Current deployment limits
-------------------------
This is a tested preview for managed PMS templates, not a public anonymous
upload service or a claim of feature parity with Carbone. No built-in TLS,
customer billing, UI, JWT/SSO, webhook delivery, remote storage, HA, or full
Excel calculation engine. Registry releases are amd64 until arm64 gets its
own integration gate. Automated restart tests are not sustained-load or
power-loss testing. Advanced Office formats and functions remain on the roadmap.
